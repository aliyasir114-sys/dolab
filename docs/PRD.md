# دولاب | DOLAB — وثيقة متطلبات المنتج (PRD)

الإصدار 0.3 · 2026-11-16 · مالك المنتج: Ali

## 1. الملخص

دولاب تطبيق دولاب إلكتروني: يسجّل المستخدم ملابسه من صوره، فيقترح التطبيق إطلالات يومية مما يملكه فعلاً، ويتيح تجربتها افتراضياً، وبيعها أو التبرع بها. يضم قسماً لتراث أزياء شعوب العالم وسوقاً داخلياً للملابس والموضة فقط.

- **المنصات:** موقع إلكتروني + تطبيق Android، بحساب واحد ومزامنة بينهما.
- **الانتشار:** المنتج (الدولاب، اللغات، التصميم) عالمي منذ البداية. توافر السوق والتبرع عبر الجهات والتوصيل يُفتح بلداً بلداً بعد التحقق من التشغيل الفعلي فيه. **اللغات:** العربية والإنجليزية.
- **الجمهور:** الرجال والنساء.
- **الهوية:** سوداني الصنع؛ أسود `#080808` وأبيض `#F5F5F5` ودرجات رمادية فقط. الهوية السودانية تظهر بأيقونة بسيطة (أهرامات نوبية بخط رفيع) لا بالاسم أو العلم أو الخريطة.

## 2. الأهداف وما ليس هدفاً

**الأهداف**
1. أن يبني المستخدم دولابه الرقمي بأقل جهد إدخال يدوي.
2. أن يعود يومياً لاقتراح إطلالة من ملابسه المتاحة.
3. أن يستفيد من القطع المهملة: ارتداءً أو بيعاً أو تبرعاً.
4. سوق موثوق لا يُنشر فيه منتج قبل المراجعة.

**ليس هدفاً في الإصدار الأول**
- الدفع الإلكتروني والمحفظة (السوق يبدأ بالتواصل والطلبات).
- تطبيق iOS.
- خزانة العائلة.
- التعرف على هوية الوجه (استخراج الملابس لا يتطلب بصمة وجه).

## 5. المتطلبات غير الوظيفية

- **الخصوصية:**
  - الصور والقياسات بيانات حساسة؛ تشفير أثناء النقل والتخزين.
  - صور الدولاب خاصة افتراضياً؛ تُعرض بروابط مؤقتة موقّعة، لا بروابط عامة أو قابلة للتخمين.
  - الأصل والمصغّرة والنسخة المعالجة ملفات منفصلة، لكل منها غرض ومدة احتفاظ.
  - حذف القطعة أو الحساب يحذف ملفات الصور فعلياً، والنسخ الاحتياطية وفق جدول معلن.
  - لا تُستخدم الصور أو القياسات لتدريب النماذج دون موافقة منفصلة وصريحة يمكن سحبها.
  - لا تعرّف على الوجه ولا قاعدة هوية بيومترية.
  - وصول الإدارة إلى صور المستخدمين مقيّد ومسجّل، وغير متاح لموظفي الدعم افتراضياً.
- **الأمان:**
  - كل سجل (قطعة، صورة، طلب) يتحقق من ملكية المستخدم له.
  - كلمات المرور تُخزَّن بخوارزمية مخصصة لكلمات المرور (scrypt)، لا بتشفير قابل للعكس.
  - تحديد معدل محاولات الدخول، وحماية استعادة الحساب، وتدوير رموز التحديث وإبطالها.
  - التحقق من نوع الملف المرفوع وحجمه ومحتواه، لا من امتداده فقط.
  - الأسرار خارج المستودع؛ `.env.example` بلا قيم حقيقية.
  - نسخ احتياطي مشفّر واختبار استعادة دوري.
  - سجل تدقيق للعمليات الحساسة لا يحوي كلمات مرور أو رموزاً أو محتوى صور.
  - HTTPS دائماً، وفحص دوري لثغرات المكتبات.
- **الأداء:** فتح الدولاب خلال ثانيتين (الهدف مبدئي: يُعرَّف حجم الدولاب والجهاز وسرعة الشبكة وطريقة القياس قبل اعتماده)؛ معالجة الصور تتم في الخلفية مع إشعار عند الانتهاء.
- **الاتصال:** التطبيق يعمل على شبكات ضعيفة؛ صور مضغوطة ومصغّرات. دون اتصال: قراءة الدولاب أولاً، ثم تعديلات القطع عبر طابور محلي يُزامَن لاحقاً، مع إظهار حالة المزامنة. عند تعارض تعديلين على جهازين يُعتمد الأحدث، ولا يعيد تعديل محلي قديم بياناتٍ حُذفت من الخادم.
- **التدويل:** RTL/LTR، عملات متعددة، مقاسات متعددة الأنظمة (EU/US/UK).
- **إمكانية الوصول:** تباين نص 4.5:1 على الأقل، مساحات لمس 44 بكسل، تسميات لقارئ الشاشة.
- **تكلفة الذكاء الاصطناعي:** حد استخدام لكل مستخدم في الباقة المجانية.

## 6. نموذج البيانات (مبدئي)

| الكيان | أهم الحقول |
|---|---|
| `User` | id, email, phone, locale, account_type (individual/store/designer/admin) |
| `Profile` | user_id, height_cm, weight_kg, usual_size, body_shape, face_shape |
| `Item` | id, user_id, name, category, primary_color, secondary_colors, color_confidence, color_confirmed, status, purchase_date, added_at, purchase_price, currency, wear_count, last_worn_at |
| `ItemPhoto` | id, item_id, url, quality_flags |
| `Outfit` | id, user_id, occasion, item_ids, is_complete, missing_listing_id |
| `WearLog` | id, user_id, item_id, outfit_id, worn_on |
| `Listing` | id, seller_id, item_id (اختياري), title, price, currency, size, condition, kind (new/used/heritage), review_status |
| `ListingReview` | id, listing_id, step, result, reason, reviewer_id |
| `Donation` | id, user_id, item_ids, recipient_type (charity/person), charity_id, confirmed_at |
| `Charity` | id, name, country |
| `HeritageEntry` | id, region, country, name, origin, occasions, how_to_wear |

كل المعرّفات UUID عشوائية لا أرقام متسلسلة. المبالغ المالية أعداد عشرية مضبوطة لا floating point. كل تغيّر في حالة القطعة يُسجَّل في `ItemStatusChange`، والتبرع يربط القطع عبر `DonationItem` لا عبر قائمة. إعلان السوق (`Listing`) كيان مستقل عن قطعة الدولاب، وربطه بها اختياري.

قواعد الاتساق: لا تُقترح إلا القطع بحالة `available`. تسجيل الارتداء مرة واحدة لكل قطعة في اليوم. عند إلغاء إعلان بيع أو رفضه تعود القطعة إلى `available`.

`Item.status`: `available`, `laundry`, `repair`, `stored`, `for_sale`, `donated`, `lost`.
`Listing.review_status`: `uploaded`, `auto_checked`, `content_reviewed`, `seller_confirmed`, `approved`, `published`, `rejected`.

## 7. الواجهة البرمجية (مبدئي)

| المسار | الوظيفة |
|---|---|
| `POST /auth/register`, `POST /auth/login`, `POST /auth/google` | الحساب |
| `GET/PUT /me/profile` | الملف الشخصي |
| `GET/POST /items`, `GET/PATCH/DELETE /items/{id}` | الدولاب |
| `POST /items/extract` | رفع صور واستخراج القطع (مهمة خلفية) |
| `GET /outfits/today?occasion=` | اقتراحات اليوم |
| `POST /outfits/{id}/wear` | تسجيل الارتداء |
| `GET/POST /listings`, `POST /listings/{id}/confirm` | السوق |
| `GET /admin/reviews`, `POST /admin/reviews/{id}` | مراجعة المنتجات |
| `POST /donations`, `GET /donations` | التبرع |
| `GET /heritage?country=` | التراث |
| `GET /me/dashboard` | لوحة الموضة |
| `GET /me/export` | تصدير بيانات المستخدم |

هذا الجدول مبدئي وليس عقداً. العقد الفعلي هو مواصفة OpenAPI التي يولّدها الخادم (`/docs`)، وكل المسارات تحت `/v1`.

### نطاق التجربة الأولى (قرار المالك، 2026-11-16)

التجربة الأولى مع مجموعة صغيرة تقتصر على الدولاب اليدوي: الحساب (تسجيل، دخول، استعادة، تصدير، حذف)، إضافة القطع يدوياً مع صورة، عرضها وتعديلها وحالاتها والبحث فيها، والمزامنة بين الموقع و Android.

معيار القبول: مستخدم جديد ينشئ حساباً، يضيف ويعدّل ويحذف 10 قطع، يراها بعد الدخول من جهاز آخر، ويصدّر بياناته أو يحذف حسابه، دون أن يصل إلى بيانات غيره.

يُؤجَّل إلى ما بعد قياس هذه التجربة: استخراج الملابس آلياً، المستشار، التبرع (مبنيّ في الخادم ويبقى مخفياً في الواجهات)، السوق (يبدأ في بلد واحد)، التراث، والتجربة الافتراضية. لا شيء من هذه حُذف من الرؤية؛ تغيّر الترتيب فقط.

## 9. مقاييس النجاح

- نسبة المستخدمين الذين أضافوا 10 قطع أو أكثر في أسبوعهم الأول.
- نسبة المستخدمين الذين يضغطون «سأرتديها اليوم» ثلاث مرات أسبوعياً.
- نسبة الألوان المستخرجة التي أكدها المستخدم دون تصحيح.
- عدد القطع المتبرع بها والمباعة شهرياً.
- زمن مراجعة المنتج من الرفع إلى النشر.
- نسبة من أكملوا التسجيل وأضافوا أول قطعة، ومتوسط زمن إضافة قطعة.
- المستخدمون النشطون أسبوعياً وشهرياً، والاحتفاظ بعد 7 و30 يوماً.
- نسبة نجاح المزامنة، ومعدل حذف الحساب.
- تكلفة التخزين والمعالجة لكل مستخدم نشط.

الأرقام المستهدفة تُحدَّد بعد أول إطلاق تجريبي.

## 10. أسئلة مفتوحة

1. شكل الإطلاق: نسخة أولية ثم تطوير تدريجي (المفترض حالياً) أم إطلاق متكامل؟
2. السوق: أفراد ومتاجر معاً (المفترض حالياً) أم المتاجر أولاً؟
3. ما الجهات الخيرية الأولى التي تظهر في قائمة التبرع، وفي أي بلدان؟
4. من يكتب ويراجع محتوى قسم التراث؟
5. حدود الباقة المجانية وأسعار الاشتراك.
6. مزوّد نماذج استخراج الملابس والتجربة الافتراضية: يُبدأ بنموذج جاهز خلف واجهة قابلة للاستبدال، بعد مقارنة التكلفة لكل 1000 صورة.
7. البلد التجريبي الأول للسوق (تقرّر أن يبدأ السوق في بلد واحد؛ البلد لم يُحدَّد).
8. فصل الأدوار (`Role`, `Store`, `StoreMember`) عن `account_type` — يُحسم عند بدء السوق.
