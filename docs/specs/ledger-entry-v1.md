# مواصفة إدخال سجل الحذف، الإصدار 1 / Deletion ledger entry, version 1

**الحالة:** معتمدة للتنفيذ (الخطة 4.10.1 و4.10.1ج). **المتجهات:** [`ledger-entry-v1-vectors.json`](ledger-entry-v1-vectors.json). **التنفيذ في الخادم:** `services/api/app/ledger.py`.

سجل الحذف يضمن ألا تعود بيانات حذفها صاحبها بعد استعادة نسخة احتياطية. كل حذف حساب أو قطعة أو صورة يُكتب إدخالاً موقّعاً في حاوية منفصلة، فيه معرّفات فقط بلا بيانات شخصية. الخادم يوقّع، ومهمة المطابقة وسكربت الاستعادة يتحققان. **الثلاثة يجب أن يبنوا البايتات نفسها حرفياً**؛ لذلك يُوقَّع نص ثابت الصيغة، وJSON مجرد وعاء للتخزين.

## 1. البايتات الموقّعة

ترميز UTF-8 (وكلها ASCII فعلياً) للنص التالي، بهذا الترتيب بالضبط، وكل سطر ينتهي بـ LF واحد (`0x0A`)، بلا CR وبلا مسافات:

```
DOLAB-LEDGER-ENTRY
v=1
key_id=<key_id>
entry_id=<uuid>
entity_type=<entity_type>
entity_id=<uuid>
user_id=<uuid>
deleted_at=<timestamp>
```

| الحقل | القاعدة (أي مخالفة = رفض الإدخال، لا تصحيحه) |
|---|---|
| السطر الأول | الثابت `DOLAB-LEDGER-ENTRY`: **فصل المجال**. توقيع على هذه البايتات لا يصلح لأي صيغة أخرى يوقّعها المفتاح نفسه، والعكس |
| `v` | `1` بالضبط. أي قيمة أخرى: «إصدار غير مدعوم» |
| `key_id` | `[a-z0-9-]{1,32}`، معروف في قائمة المفاتيح العامة. داخل البايتات الموقّعة، فلا يُنسب الإدخال إلى مفتاح آخر |
| `entry_id`، `entity_id`، `user_id` | UUID بأحرف صغيرة، 36 حرفاً بالشرطات (`8-4-4-4-12`) |
| `entity_type` | `item` أو `photo` أو `user` |
| `deleted_at` | UTC بالصيغة `YYYY-MM-DDTHH:MM:SS.ffffffZ`: ستة أرقام للأجزاء بالضبط، وحرف `Z` لا `+00:00`، وتاريخ ووقت حقيقيان |

- لا قيمة يمكن أن تحتوي `=` أو LF بحكم قواعدها، فالفصل بين الحقول لا لبس فيه.
- كل حقل مرة واحدة، والترتيب ثابت، ولا حقول اختيارية.

## 2. التوقيع

- **Ed25519** (RFC 8032، النسخة الأساسية؛ لا `Ed25519ph` ولا `Ed25519ctx`) على البايتات أعلاه. الناتج 64 بايتاً.
- يُخزَّن بترميز base64url **بلا حشو** (`=`): 86 حرفاً بالضبط، بتهجئة واحدة فقط (يُرفض أي ترميز آخر لنفس البايتات).
- المفتاح الخاص: بذرة Ed25519 من 32 بايتاً بترميز base64url بلا حشو (43 حرفاً) في `DOLAB_LEDGER_SIGNING_KEY`، عند الخادم وحده، ومنفصل عن مفتاح الرموز.
- المفاتيح العامة للتحقق: `key_id:base64url` مفصولة بفواصل.
- بيئة التوقيع مدخل صريح إلى دالة التوقيع: `development` أو `test` أو `staging` أو `production`. تُرفض البيئة المفقودة أو غير المعروفة؛ ويُرفض التوقيع بمفتاح الاختبار المنشور في `staging` و`production` عند نقطة التوقيع نفسها.
- Ed25519 حتمي: التوقيع لبيانات ومفتاح معينين ثابت دائماً، ولذلك تصلح المتجهات للمقارنة حرفاً بحرف.

## 3. الكائن المخزَّن

اسمه `YYYY/MM/DD/<entry_id>.json`، والتاريخ من `deleted_at`. محتواه JSON مضغوط بهذا الترتيب:

```json
{"v":1,"key_id":"…","entry_id":"…","entity_type":"…","entity_id":"…","user_id":"…","deleted_at":"…","sig":"…"}
```

القارئ لا يعتمد على هذا الترتيب ولا على المسافات (SIG3): البايتات تُبنى دائماً من القالب.

## 4. التحقق (مهمة المطابقة وسكربت الاستعادة)

1. قراءة JSON بحد **2048 بايتاً**، ورفض: أي مفتاح زائد أو ناقص أو مكرر؛ أي قيمة ليست نصاً، عدا `v` عدداً صحيحاً (لا نص، ولا عدد عشري، ولا قيمة منطقية)؛ و`NaN` و`Infinity`.
2. `v` غير 1: «إصدار غير مدعوم». ثم التحقق من كل قيمة بقاعدتها **دون أي تطبيع** (لا تحويل أحرف، ولا إضافة أصفار).
3. اسم الكائن يطابق `entry_id` وتاريخ `deleted_at`.
4. `key_id` معروف، ثم بناء البايتات بالقالب والتحقق من التوقيع بالمفتاح العام المقابل له.
5. أي فشل يُسجَّل ويُنبَّه عنه، **ولا يحذف شيئاً**.

رموز الرفض في التنفيذ والمتجهات: `too_large`، `not_json`، `bad_keys`، `bad_type`، `unsupported_version`، `bad_value`، `name_mismatch`، `unknown_key`، `bad_signature`.

## 5. متجهات الاختبار

`ledger-entry-v1-vectors.json` فيه:

- `rfc8032_test_1`: متجه RFC 8032 الأول، للتأكد من أن مكتبة التوقيع نفسها سليمة.
- `keys`: زوجا مفاتيح **للاختبار فقط** (`test-1`، `test-2`). بذورهما منشورة هنا عمداً، فهما **ليسا سريين**، ويرفض مسار التوقيع استعمالهما في staging والإنتاج (SIG10).
- `valid`: إدخالات صالحة لكل نوع، مع البايتات الموقّعة بالست عشري والتوقيع المتوقع، ومعها نسختا SIG3 (مفاتيح بترتيب آخر، ومسافات).
- `invalid`: حالات رفض مسمّاة برقم اختبار الخطة (SIG2، SIG4–SIG9) ورمز الرفض المتوقع.

**كيف صُنعت:** بتنفيذ RFC 8032 المرجعي (القسم 6، بايثون صرف)، مستقل عن شيفرة الخادم ومكتبتها؛ ويتحقق CI بمكتبة `cryptography` المثبّت إصدارها من أن الخادم ينتج البايتات والتوقيعات نفسها حرفاً بحرف (SIG1). كل مكوّن لاحق (مهمة المطابقة، سكربت الاستعادة) يُختبر على هذه المتجهات نفسها.

## 6. تغيير الصيغة

صيغة جديدة = `v=2` بمواصفة ومتجهات جديدة. خلال الانتقال يقبل المتحقق الإصدارين، ثم يُسحب الأول بعد 31 يوماً من آخر إدخال به. هذا الملف لا يُعدَّل بما يغيّر البايتات أو قواعد القبول.

## 7. الاختبارات (الخطة 4.10.1ج)

| رقم | الاختبار | المتوقع | الخادم |
|---|---|---|---|
| SIG1 | المكوّنات على المتجهات | البايتات والتوقيعات المتوقعة حرفاً بحرف، وقبول كل متجه صالح | `test_ledger.py` |
| SIG2 | حرف واحد مختلف في كل حقل | رفض | ✓ |
| SIG3 | ترتيب مفاتيح JSON أو مسافاته | قبول | ✓ |
| SIG4 | مفتاح زائد أو ناقص أو مكرر، أو `v` نصاً | رفض | ✓ |
| SIG5 | UUID بأحرف كبيرة، أو `+00:00`، أو ثلاثة أرقام للأجزاء | رفض دون تصحيح | ✓ |
| SIG6 | `v=2` | «إصدار غير مدعوم» | ✓ |
| SIG7 | `key_id` مجهول، أو لمفتاح معروف آخر مع توقيع الأصل | رفض | ✓ |
| SIG8 | اسم الكائن لا يطابق | رفض | ✓ |
| SIG9 | توقيع صالح على البايتات دون السطر الأول | رفض | ✓ |
| SIG10 | مفتاح الاختبار في staging أو الإنتاج، أو بيئة توقيع مفقودة/غير معروفة | رفض من نقطة التوقيع | ✓ |
